# ppt-design-system

잘 만든 기존 덱 여러 개를 **25개 기준**(컬러 7 · 폰트 7 · 레이아웃 9 · 구조 3 · 특이점 5)으로 분석하고, 여러 덱에 **반복되는 것만** 「디자인 공통 요소」(COMMON.md) 한 장에 모은다. 새 덱은 이야기 층을 먼저 짠 뒤 그 기준으로 만들고, 고친 점은 일반화·검수해 「지침」으로 쌓는다(한 번 한 수정은 두 번 말하지 않는다).
스킬 폴더: `SK="${CYS_PACK_DIR:-$HOME/.cys/pack}/skills/ppt-design-system"`
- 25기준 원문 = `$SK/references/heidi-guideline.md`(지은이 헤이디 · 원문 동봉 · 출처 머리말)
- 이야기 층 절차 = `$SK/references/story-first.md`
- 근거표 도구 = `$SK/tools/pptx_design_extract.py`(python3 표준 라이브러리만)
- 빈 공통 양식 = `$SK/templates/COMMON.md`

## ① 언제 쓰나

- 사용자가 기존 PPT 를 주며 「이 디자인을 분석해」「이런 식으로 새로 만들어」「우리 회사 PPT 기준을 세워」라고 할 때.
- 이미 쌓인 `COMMON.md` 기준으로 새 덱을 만들 때 · 덱 수정 요청을 다음 덱에도 남기고 싶을 때.
- 쓰지 않을 때: 정해진 스타일 11종에서 골라 바로 `.pptx` 를 뽑는 일 = `ppt-styles` · 영상 보고 = `video-report-deck`.

## ② 순서

**준비** — 작업 폴더를 사용자와 정한다(예 `<작업폴더>/design-system/`). 처음이면 `cp "$SK/templates/COMMON.md" <작업폴더>/design-system/COMMON.md` 후 머리의 조직 이름·날짜를 채운다. 결과는 전부 작업 폴더에 쓴다(팩 폴더 `$SK` 에는 쓰지 않는다).

**A. 덱 분석(덱 1개마다)**
1. 근거표: `python3 -I "$SK/tools/pptx_design_extract.py" "<덱.pptx>" --out "<작업폴더>/design-system/decks/<덱이름>/"` → `<덱이름>.design.md`(테마 색·글꼴 · 크기 위계 · 굵게 · 글자 색 · 도형 채움 · 장별 여백 · 상자 면적 · 글자 수 · 근거 장 번호) + `.design.json`.
   - .ppt(옛 형식)·.key·.odp 는 먼저 pptx 로: `soffice --headless --convert-to pptx <파일>` (키노트는 「파일 → 내보내기 → PowerPoint」) · 변환본임을 기록한다.
2. 분석 쓰기: `heidi-guideline.md` 의 기준 1-1 ~ 5-5 순서 그대로 `decks/<덱이름>.md` 에 쓴다. 숫자는 근거표에서 옮기고, 해석 문장 끝에 근거 장 번호.
3. 대표 슬라이드 5장(5-4): `soffice --headless --convert-to pdf <덱.pptx>` → `pdftoppm -png -r 80 -f N -l N <덱.pdf> decks/<덱이름>/rep-NN`. 글꼴이 바뀌어 보이면 `pdffonts` 로 확인하고 그 사실을 적는다(PowerPoint·Keynote 로 PDF 를 뽑아 대신해도 된다).

**B. 공통 요소 갱신(덱 2개 이상)**
- `COMMON.md` 각 절에 「N개 덱 중 M개 · 근거 덱」을 붙여 반복 요소만 적는다. 한 덱에만 있는 것은 그 덱 파일의 5-3(예외)에. 고객사·행사 고유 색·로고는 넣지 않는다.

**0. 이야기 층 먼저(새 덱의 기본 절차)** — `references/story-first.md` 그대로: 먼저 정할 5칸 → 덱 갈래(설득·가르침·안내) → 덱 메시지 → SCQA 줄거리 → 주장 문장 제목 → 제목만 읽기 시험 → 논리 모양 레이아웃 → `STORY.md`. 이것을 통과한 뒤에만 C 로 간다.

**C. 새 덱 디자인**
- 받을 것 = 비율(기본 16:9) · 메인·서브 색 · 글꼴 · 내용 원고. 나머지(여백·카드·강조 방식·위계)는 `COMMON.md` 로.
- 만들기 = `ppt-styles` 스킬의 키트(`lib/kit.js` · `lib/theme.js` · pptxgenjs)로 COMMON 값을 코드에 넣어 만든다. 기본 규칙(사용자가 따로 정하지 않았으면): 본문 24pt 기준 · 카드 안 16pt 이상 · 원문 용어 그대로.
- 7장 이상이면 앞 5장을 먼저 만들어 렌더·검수하고, 거기서 나온 규칙(글 폭·표 높이·그림 자리)을 고친 뒤 나머지를 만든다.
- 결과 = .pptx + PDF 를 사용자에게 경로와 함께 보인다.

**D. 수정 → 일반화 → 지침**
1. 수정 요청을 반영해 다시 만든다.
2. 「이 덱에만 맞는 것」은 빼고 「모든 덱에 통하는 문장」 후보를 만들어 보인다(예: 「알약 모양 라벨 폭은 글 길이에 맞추고 좌우 여백 1cm 미만」 · 「같은 중요도 항목 중 하나만 메인색으로 튀게 하지 않는다」).
3. **검수받은 줄만** `COMMON.md` 「지침」 절에 `· 출처 덱 · 날짜 · 검수자` 를 붙여 더한다 → 다음 덱부터 적용.

**E. 키비주얼 프롬프트(새 덱마다)**
- 덱 전체 → 핵심 메시지 1문장 → 그 느낌을 **은유·약간 추상**으로(내용을 그대로 그리지 않음) · 메인·서브 HEX · 분위기 낱말 · 「no text, no logo」 · **영어**.
- 그림이 2장 이상이면 덱 공통 앞말 1문단(그리는 방식·빛·색·시점)을 모든 프롬프트 맨 앞에 똑같이 붙인다. 글이 올라갈 그림은 비울 자리를 말로 적는다(예: left side kept empty for the title) · 비율은 들어갈 자리에 맞춘다.
- 실제 생성은 요청 때만: `media-gen-image` 스킬(종량제 → `cost-preview-confirm` 로 비용 먼저) 또는 사용자가 이미지 생성 서비스에 붙여 넣기.

## ③ 주의할 점

- ⛔ 근거표에 없는 수치를 눈대중으로 만들지 않는다. 「상속」(레이아웃·마스터에서 물려받은 값 — 도구가 풀지 않음)은 「상속」으로 적는다. 면적 비율·밀도는 상자 면적 근사이고 그림 안 색은 읽지 않는다.
- 내부 자료·개인정보가 든 덱은 디자인 수치·구조만 기록하고 본문 글은 옮기지 않는다. 외부 모델·서비스에 덱 원본을 넣지 않는다. 결과 폴더를 어디에 둘지(공유 드라이브 등) 먼저 정한다.
- 원문 지침은 노션 페이지에 기록하라고 하지만, 이 스킬은 같은 기준을 작업 폴더의 md 파일에 쓴다(누구나 바로 읽고 버전이 남는다).
- 의존: 근거표는 python3(3.8 이상)만 있으면 된다 — 없으면 맥 `brew install python` · 윈도 https://www.python.org/downloads/ . 대표 슬라이드 그림은 LibreOffice(`soffice`)와 poppler(`pdftoppm`·`pdffonts`)가 필요하다 — 맥 `brew install --cask libreoffice` · `brew install poppler` / 리눅스 `sudo apt install libreoffice-impress poppler-utils`. 없으면 그 단계는 건너뛰고 「대표 5장 그림 없음(이유)」을 분석 파일에 적는다.
- LibreOffice 렌더는 미리보기다. 맥에서 시스템 한글 글꼴을 못 찾아 대체될 수 있다 — 글꼴이 중요한 덱은 PowerPoint·Keynote 로 PDF 를 1회 뽑아 본다.

## ④ 확인하는 방법

- 덱 분석의 모든 수치가 근거표에 실재한다(`grep` 으로 1회 대조) · 대표 5장 PNG 가 실재하거나 없는 이유가 적혀 있다 · COMMON 「지침」 줄은 검수 표시가 있는 것만.
- 새 덱: ① 기계 — `python3 "${CYS_PACK_DIR:-$HOME/.cys/pack}/skills/ppt-styles/tools/check_pptx.py" <덱.pptx> --slides N --pdf`(PASS · 경고 처리) · 화면 숫자·인용 원천 대조와 노트 빠짐 0(story-first.md 「기계 점검」). ② 눈 — 장별 PNG 를 전부 본다: 화면 밖으로 나감 · 글 넘침 · 글끼리 겹침 · 대비 부족(작은 글 4.5:1 · 18pt 이상 3:1) · 받침 없이 복잡한 그림 위 글 · 깨지거나 일그러진 그림 · STORY.md 에 있는데 화면에 없는 요소 · 표지와 끝 장의 쪽 번호·총 장 수. ③ 정렬·간격처럼 취향이 섞인 것은 눈에 띄게 나쁠 때만 고친다. ④ 검수 단계에서 내용·문구·장 순서·색·글꼴은 바꾸지 않는다 — 바꿀 일이면 §0·C 로 돌아간다. 같은 대비 문제가 여러 장에 나면 색을 한 번에 정한다.
- 시험 입력 결과(2026-11-06): ppt-styles 로 만든 덱 3벌에 근거표 도구를 돌림 — ① 보통 덱(modern-minimal 4장) → OK 4장 · 글꼴 Apple SD Gothic Neo 193자. ② 지저분한 덱(150자 영한 혼합 제목 · 빈 목록 · 숫자 칸 · 6장) → OK 6장 · 크기 위계 7단계(17pt 38.7% · 44pt 24.7% …) · 글꼴은 테마에서 물려받아 「상속(테마/마스터)」 486자로 정직하게 나옴. ③ 차트 덱(research-data 3장) → OK 3장 · NanumBarunGothic 159 · NanumSquare Neo 56. `.key` 파일 → 변환 안내 + 코드 2 · 없는 파일 → 코드 2. 그룹 도형 시험(2R 수정): 중첩 그룹(바깥 off 10/10pt ⊃ 안쪽 off 90/190pt·2배 확대 ⊃ 로컬 0/0·100×50pt 도형) → 1장 여백 좌/상 100/200pt · 상자 면적 20000pt²(고치기 전 0/0 · 5000) · 위 3벌 근거표는 고치기 전 판과 글자까지 같음. 실제 사람이 만든 덱으로 25기준 분석 전체를 끝까지 해 보는 시험과 스킬 없이 대조는 하지 않았다.
