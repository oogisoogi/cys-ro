# A1-F1~F3 설계 1쪽 — 0바이트 영구 잠금 수리(잠금·게시 규약)

## 0. 공통 원칙(세 파일 모두)
1. **정확히 0바이트만** 복구 대상이다. 공백만 있는 파일 · BOM만 있는 파일 · 해석 불가 · 권한 오류 = 지금처럼 **무변경 거부**(v1.1.6 「모든 오류 = 빈 상태」 회귀 금지).
2. 0바이트 판정과 복구 쓰기는 **같은 프로세스 간 잠금 안**에서 한다(잠금 밖 판정 → 잠금 안 쓰기 금지 · 잠금 안에서 다시 읽고 판정).
3. 게시는 **완성된 임시 파일 → 원자 게시**(부분 파일이 경로에 보이는 순간 0). 임시 이름 = pid + 프로세스 안 순번(기존 관례).
4. 복구는 알린다: 무엇을 새로 만들었는지 · 무엇은 되살아나지 않는지(옛 승인 · 옛 부서).

## 1. F1 `~/.cys/.approval-secret` — `approval.rs signing_secret_at`
**잠금** = 새 헬퍼 `lock_path_exclusive(p)` = `<p>.cys-lock` 을 std `File::lock()`(Rust 1.89+ 안정 · 유닉스 = `flock(LOCK_EX)` · 윈 = `LockFileEx`)으로 잡는다. 유닉스에서는 `pack::acquire_settings_lock` 과 같은 flock 이라 서로 배제된다. 이 키 파일은 Rust(cysd)만 만진다(파이썬 동료 없음 — grep 확인) → 이종 잠금 문제 없음. `acquire_settings_lock` 의 「윈 = None」 한계를 이 파일에는 물려받지 않는다.

**절차**
```
① 잠금 없이 읽기: 비어 있지 않음 → 그 키(빠른 길 · 지금과 같음) · 권한 등 오류 → None(지금과 같음)
② 부재 또는 0바이트 → 잠금 획득
   · 잠금 실패(잠금 파일 못 만듦 등): 부재 = 지금의 게시(hard_link → 실패 시 create_new)로 · 0바이트 = None(잠금 없이 복구 안 함)
③ 잠금 안 재판독: 비어 있지 않음 → 그 키(다른 데몬이 먼저 게시) · 오류 → None
④ 부재·0바이트 확정 → 난수 32B → 임시 파일 작성 · 0600 · sync_all
⑤ 게시: 부재 = hard_link(구판 데몬과의 배제 유지 · AlreadyExists → 경로의 키) · 하드링크 불가 FS·0바이트 = rename(원자 교체)
⑥ 게시 뒤 경로를 다시 읽어 「내 키 == 경로의 키」 확인 → 같을 때만 반환 · 다르면 경로의 키(비어 있지 않을 때) · 게시 실패 = None
```
- **바뀌는 것**: `create_new` 로 빈 파일을 먼저 만들고 나중에 쓰는 길(0바이트가 생기는 원인 중 하나)은 잠금을 잡은 경우 쓰지 않는다. 게시 실패 때 「세션 한정 키」 반환을 없앤다(호출마다 다른 키라 서명이 영영 안 맞음 · 게시 실패를 성공으로 반환하지 않는다 — codex ⑵). 영향: 쓰기 불가 HOME 에서 `approval.sign` = `secret_unavailable`(지금은 「성공」이지만 쓸모없는 서명).
- **옛 승인 재서명 금지**: `approval.check` 는 **현재 키로 검증된** 기록만 갱신·재서명한다(handlers.rs:7951 `best_match` → 7957). 새 키로 바뀌면 옛 기록은 매칭되지 않아 재서명되지 않는다 — 이 성질을 시험으로 고정한다(옛 키 기록 = approved:false · 파일의 그 기록 서명 불변).
- **구판 데몬**: 1.1.6 이하 데몬은 새 잠금을 모른다 → 갱신 뒤 **기존 데몬 종료가 필요**(기록 · 갱신 절차가 이미 데몬을 재기동하는지 ⑦ 게이트에서 대조). 구판 데몬의 `create_new` 직후(쓰기 전) 빈 파일을 새 데몬이 0바이트로 보고 rename 교체하면 구판은 분리된 파일에 쓴 키를 돌려줄 수 있다(codex ⑵(b)) — 신판끼리는 잠금으로 닫히고 구판 혼재 창만 남는다(정직 고지).
- 공격자 절단(단일 UID): 키 재생성 유발 = 옛 승인 무효화(재승인 필요) · 권한 경계 우회 아님(codex ⑵(c) 그대로).

## 2. F2 `~/.cys/approvals.json` — `load_records_at`
- 잠금 = 기존 `lock_records()`(읽기·변경·저장 전 구간 · 호출부 handlers.rs 2곳 그대로) — 새 잠금 없음.
- 규칙: 읽은 바이트가 **정확히 0** → 빈 목록 `Ok(vec![])`. 선두 BOM(`\u{feff}`) 하나를 벗긴 뒤 해석(부서 목록 판독과 같은 규칙) — 벗긴 뒤 해석 실패 = 지금처럼 Err(BOM 파일 전체를 빈 목록으로 접지 않는다). BOM만 있는 파일 = 0바이트 아님 → Err.
- 저장은 기존 `save_records`(tmp → rename). 이전 승인 내용은 복원되지 않는다(0바이트엔 복원할 것이 없다) → 재승인 필요.
- 윈: `lock_records()` = None(기존 한계 · 이번 수리로 넓어지지 않음). 잠금 없는 두 데몬이 동시에 0바이트를 읽고 저장하면 한쪽 새 기록이 빠질 수 있다(= 기존 lost-update 와 같은 창).
- 읽기 전용 호출부(schedule.rs:933)는 0바이트 = 빈 목록(승인 없음 = 막는 쪽 · 쓰기 없음).
- 시험 수정: approval.rs:851 「BOM = Err」 단언 → 「BOM + 유효 JSON = 그 기록」 · 「BOM + 손상 = Err」 로.

## 3. F3 `~/.cys/depts.json` — `cys-dept reg_init` 외
- **reg_init** 재작성: 빠른 길 `[ -s "$REG" ] && return 0`(있고 비어 있지 않음 = 지금처럼 무동작 · 셸만) → 그 밖(부재·0바이트)만 파이썬 1회: 기존 쓰기 동사와 **같은 잠금**(`$REG.lock` · fcntl.flock / 윈 msvcrt 관례 그대로) 안에서 재판정 → 부재 또는 0바이트면 `{"depts":{}}` 를 tmp + `os.replace` 로 게시. 비어 있지 않으면(그 사이 누가 씀) 무동작. 잠금 밖 `printf >` 제거.
- **알림 구분**: 부재에서 처음 만들 때 = 무음(지금과 같음). **0바이트를 초기화했을 때만** stderr 1줄: 「부서 목록 파일이 비어 있어(0바이트) 빈 목록으로 다시 만들었습니다 — 목록 초기화이지 복구가 아닙니다. 전에 있던 부서 폴더와 실행 중인 부서는 목록에 돌아오지 않습니다」.
- **같은 규칙을 판독·쓰기 블록에도**: `reg_read_py` 와 잠금 안 RMW 블록(reg_upsert·reg_remove·reg_fence_close·reg_set_meta·reg_set_field 등 `utf-8-sig` 로 읽는 곳 전수)에 「크기 0 = `{"depts":{}}`」 한 줄 — reg_init 복구가 권한 등으로 실패했을 때도 판독·쓰기가 같은 판정을 쓴다. 비어 있지 않은 손상 = exit 12 그대로.
- **cys-dept 밖 1.1.7 엄격 판독자 2곳**(①에서 엄격해진 곳 — v1.1.6 대비 회귀면): `javis_dept_request.registry()`(0바이트 → `{}` · 읽기 전용) · GUI `src-tauri main.rs list_depts_at`(0바이트 → `{"depts":{}}` · 읽기 전용 · 「부서 목록을 읽을 수 없음」 토스트 소멸). 둘 다 쓰지 않는다(복구는 cys-dept reg_init 한 곳).
- 그 밖 판독자(javis_org·phoenix·formation·lib.rs 등)는 1.1.7에서 엄격해지지 않았다(①의 대상 아님)【④ 단계에서 0바이트 거동 실측으로 확인】.
