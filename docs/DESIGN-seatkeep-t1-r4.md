## 1. 뿌리 고침안

### A. 멱등 키 + 정직한 비성공(R1·R2 · CLI 쪽)
1. **멱등 키에 대화 ID**: 잇는 기동(`resume` ∧ 대화 있음)이면 `la-{role}-{agent}-{cwd 해시}-s{정규화 대화 id}` · 새 대화 기동은 종전 키 그대로. 키는 데몬에 **불투명 문자열**이다(`create_idem` 은 문자열 일치만 · handlers.rs `idempotency_key`) → **데몬·규약 변화 없음 · 옛 데몬 호환**. 효과: S 의 기동은 T 좌석을 다시 받지 않는다. 같은 S 의 재시도(응답 유실)만 같은 좌석을 받는다 = 멱등의 본래 뜻.
   - 귀결(새 동작 1): 역할 R 에 T 좌석 W 가 살아 있을 때 S 를 잇는 기동은 **새 좌석**을 만든다 — 비특권 역할 = 데몬 latest-wins(역할 이름이 새 좌석으로) · `worker` = `worker-N`. 지금도 120초가 지난 뒤면 똑같이 되므로 새 길이 아니라 「120초 안」만 「120초 뒤」와 같아진다.
2. **재반환 좌석 판정 = 세 갈래(등록 없음 ≠ 다른 대화)** — 재반환 + 에이전트 살아 있음일 때만(이제 「같은 S 의 앞 호출이 띄운 좌석」이 정상 경우):
   - 잇는 중 확인(등록 대화 = S · 또는 그 좌석 자손 argv 에 S = 기존 `lease_find_writer`) → 종전 rc 0 · 임대 = 그 좌석 · 작성자 기록.
   - 다른 대화 확인(등록 대화 = T ≠ S) → **rc 93** · 임대 되돌림(그 좌석은 S 를 안 씀) · 「· R: 대화 S — 그 역할 좌석 surface:W 가 다른 대화를 잇는 중이라 띄우지 않음 · 확인: `cys read-screen --surface surface:W`」.
   - 판정 불가(등록 없음 ∧ argv 없음 · 또는 topology 판독 실패) → **rc 93** · 임대 **유지**(결과 불명 = 엄격 판정 · 종전 보수 쪽) · 「… 작성자 생존 판정 불가 — 확인: …」.
   - rc 는 **새로 만들지 않는다**(93 재사용) → `cys restore`(commit 0 · ok 0 · `lease_unknown` 계수 · 요약 꼬리 「생존 판정 불가 N」) · `javis_boot_node`(`resume_refused`) · Tauri 판정 층(93 사람말) 이 이미 받는다.
   - 기록 장치: 지금의 「좌석 → 잇는 기동이었나(bool)」 기록을 세 값(잇는 중 · 안 씀 · 모름)으로 넓혀 `lease_finish_by_rc`·`lease_settle_kept_rc` 가 93 일 때 되돌림/유지를 가른다(호출 결과로 받는 편이 낫다 — `run_launch_agent_opts` 반환에 처분을 싣는 것도 후보 · 구현 때 택).

### B. pending 후속 감시(R3 · 앱 쪽)
1. 120초 시점의 「사이드카 0」은 유지(794 r2).
2. done 을 낸 뒤 **pending 인 끝점(본부·부서)마다 후속 감시 태스크 1개**: 5초마다 일회성 `org.status`(2초 시한) → **명시 `done`·`off`** 를 받으면 그때 판정 층(`run_sidecar_restore_judged`) 1회 → 결과를 화면에 합류(성공 = 「늦게 확인됨」 · 비성공 = 종전 사람말 `restore_note`/부서 사정 알림 = 92·93·관문·실패 모두) → 끝점이 모두 끝나면 이벤트 `restore-progress {phase:"settled", …}`(새 단계 · 앱→화면 내부 이벤트 · 가산) → 화면이 그때 옛 자리 쓸기를 무장.
3. 후속 감시 상한 30분 → 넘으면 sticky 경고 1장 「자동 복원이 30분 넘게 끝나지 않습니다 — ↻ 재시작을 눌러 다시 시도하세요」 + 감시 종료(영구 running 의 사람 안내). ⚠데몬 쪽 자동 복원 자식 `child.wait()` 무제한(cysd main.rs)은 **T1 밖 📌**(데몬 취소·인계 규약 = 새 티켓).
4. 진행 표시: 끝점 대기 진입마다 「직원 복귀 중」 sticky 를 다시 띄워 수명 갱신(#6) · pending 동안은 「확인 중」 sticky(상한 30분).

### #7 알려진 한계(codex r4 판정문 원문 · 1.1.16 후보)

> **major · 확신도 높음 — 앱을 종료했다 다시 열면 pending 감시와 30분 안내가 사라진다**
> 근거: 감시 대상은 프로세스 메모리에만 있다. pending이 정해지기 전에 업데이트 마커를 제거하고 현재 버전을 기록한다. 같은 버전 재실행은 `PendingUpdatePlan::Skip`으로 복원·감시를 시작하지 않는다(:4125·:4157).
> 재현: macOS에서 데몬은 계속 running·앱은 pending 감시 중 → 앱 프로세스 종료 → 같은 버전 앱 재실행 → 옛 감시는 소멸하고 새 감시는 없음 → 이후 done의 사람말도, 영구 running의 30분 안내도 없음.
> 고침 방향: 미해결 감시 상태를 보존하거나, 앱 기동 시 끝점의 자동 복원 상태를 재조정해 감시를 재개해야 한다.

- r5 축소 뒤의 같은 갈래: 「30분 안내」 = 이제 「⚠ 직원 복귀를 확인하지 못함」 sticky — 앱을 다시 열면 그것도 없다. 첫 회차 done 은 이미 「진행 중」(완료 아님)을 말했고 쓸기 무장도 없었으므로 거짓 「완료」·옛 자리 쓸기는 생기지 않는다(사람말이 빠지는 쪽).
