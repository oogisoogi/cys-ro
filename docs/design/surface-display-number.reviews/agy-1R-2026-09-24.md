FINDINGS:
- [심각도 높음] <§3-2 ③, §2-1 ⑥> 메모리 상태 `holders`의 타입 한계로 인해 런타임 `spawn_failed` 막힘 예외 규칙 구현 불가 — 근거: §2-1 ⑥은 PTY 생성 실패 시 할당기가 해당 번호를 막힘으로 치지 않는다고 했으나, §3-2 ③의 `holders` 타입(`(surface_id, Option<f64>)`)은 정상 닫힘 시각과 실패를 구분할 수 없고 과거 상태로 롤백할 방법도 제공하지 않아 런타임 PTY 실패 시 해당 번호가 W시간 동안 부당하게 막히게 됨 — 제안: `holders`의 상태 타입을 확장(`enum State { Running, Closed(f64), SpawnFailed }`)하거나, 할당 시 이전 상태를 임시 저장했다가 실패 시 복원하도록 명시.
- [심각도 중간] <§3-2 ②> 런타임 시 메모리 할당기 상태(`holders`) 갱신 절차 누락 — 근거: 좌석 만들기 및 닫기 흐름에서 DB INSERT/UPDATE만 서술되어 있으며 인메모리 `holders` 배열 갱신이 빠져 있음. 설계대로 캐시 갱신을 누락 구현할 경우 할당기가 과거 메모리를 참조하여 보이는 번호 중복(불변식 I2 위반)이 즉시 발생함 — 제안: 만들기 완료 시 `holders[c] = (id, None)`, 닫기 완료 시 `holders[c] = (id, now)`로 메모리를 동기 갱신하는 단계를 명시적으로 추가.
- [심각도 중간] <§9> DB I/O 실패 시 할당기 폴백(Fallback) 동작을 검증하는 시험 부재 — 근거: §3-2 ⑤에서 디스크 가득 참 등으로 쓰기 실패 시 패닉 없이 메모리로 번호를 할당해 시스템 전멸(4군 ③)을 막는 핵심 생존 장치를 설계했으나, 시험 표(§9)에는 디스크 쓰기 오류를 주입하여 이 방어선이 실제로 작동하는지(생성이 안 막히는지) 검증하는 항목이 없음 — 제안: Mock DB 또는 읽기 전용 환경을 구성하여, 쓰기 실패 시 `surface.numbers_write_failed` 이벤트가 발생하면서도 좌석은 정상 반환되는지 확인하는 테스트 추가.
